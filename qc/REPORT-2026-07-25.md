## This run: fixed a real, live pricing bug (audit finding H4) — non-monotonic tiered pricing

**Found:** `pricingService.calculatePrice` multiplied the *entire* page count
by whichever single tier's rate matched the count (`pageCount >= tier.threshold`,
highest matching threshold wins), then applied that flat rate to every page.
Consequence: crossing a tier boundary could make a **larger book cost less** —
49 pages cost $24.50 (49 × $0.50) but 50 pages cost $20.00 (50 × $0.40). Same
cliff at 99 → 100 pages ($39.60 → $30.00). This was not just a latent bug:
`server/core.test.ts` had a test explicitly titled `"tier-2 discount means
price(50) < price(49)"` that asserted the drop as **intended** behavior,
alongside a *different* test in the same file asserting monotonicity
*within* each tier only — the two blocks contradicted each other, and the
cross-tier case (the actual bug) was the untested gap between them.

**Why this matters:** this pricing function is live on the `books.upload`
path (`totalPrice = calculatePrice(metadata.totalPages)`) and the
`books.calculatePrice` query procedure — it is what a user would see quoted
for their book. A pricing function where adding pages can *lower* the price
is a real revenue/trust problem (a customer could pad a PDF to hit a cheaper
bracket), not a "volume discount" as the removed test comment characterized
it.

**Fix:** rewrote `calculatePrice` (and the `subtotal` field of
`getPricingBreakdown`) to use standard marginal/bracket pricing — each page
is billed at the rate for *its own* bracket only (bracket 1: pages 1-49 @
$0.50; bracket 2: pages 50-99 @ $0.40; bracket 3: pages 100+ @ $0.30), the
same shape as a progressive tax bracket. This is monotonically
non-decreasing by construction for any tier table whose rate decreases as
threshold increases (the only shape this app's config uses). Extracted the
bracket-walk into a new `computeTieredSubtotal` helper shared by
`calculatePrice` (clamped + rounded) and `getPricingBreakdown` (so its
`subtotal` is now the real pre-cap marginal cost, not `pageCount × top-tier-rate`,
which was inconsistent with `total` even before this fix in any case that
crossed a tier boundary).

**New prices at the same page counts (for reference):**

| Pages | Old (buggy, flat) | New (marginal) |
|---|---|---|
| 49 | $24.50 | $24.50 (unchanged — single bracket) |
| 50 | $20.00 | $24.90 |
| 51 | $20.40 | $25.30 |
| 99 | $39.60 | $44.50 |
| 100 | $30.00 | $44.80 |
| 101 | $30.30 | $45.10 |

Prices below the tier-2 threshold (≤49 pages) are unchanged since a book
fully inside one bracket prices identically under both formulas — only
multi-bracket books change, and they now cost *more*, consistent with
"more pages, more (or equal) cost, never less."

**Not touched (flagged, not a code bug, needs a business decision):** H4's
other half — `totalPrice` is computed from the PDF's *raw* page count
(`metadata.totalPages`, capped at 500 for upload validation) while actual
processing caps at `PIPELINE_MAX_PAGES` (20 pages) — so a 200-page book is
priced on 200 pages but only 20 are ever illustrated. That's a pricing
*model* question (bill for pages processed vs. pages submitted), not a
formula bug, and stays on Jerome's decision list, unchanged by this fix.
